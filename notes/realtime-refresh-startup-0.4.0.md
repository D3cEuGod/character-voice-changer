# 0.4.0：实时会话刷新、启动缓存和延迟试验

测试日期：2026-11-13 至 14。本机 i5-12400F、RTX 5060 Ti 16 GB、Windows 11、ONNX Runtime / DirectML。仍使用现有三套 RVC 权重和各自索引，没有量化、换权重或缩短语音前瞻。原始小型摘要保存在 [evaluation/0.4.0](evaluation/0.4.0/)。部分候选测试在改版本号之前执行，健康信息保留当时的 0.3.1，避免改写测量记录。

## 实时自动刷新

用户观察到长时间通话后音质下降，要求定期重开实时变声。默认阈值 3,000 包，包含停顿时的静音包：VB-CABLE 120 ms 约 6 分钟，Steam 200 ms 约 10 分钟；实际墙钟时间还包含启动、刷新和可能的处理积压。`--live-restart-packets 5000` 改成 5,000 包，`0` 关闭。

到阈值后发送尾包和 `finish`，播放完已转换的尾音，关闭采集、播放与 WebSocket。GUI 用原来的角色、强度、方式和设备创建新会话。连续降噪、VAD、音高平滑、重采样和播放 FIFO 都重新建立；后端进程和图 / 索引的全局缓存不清除。释放设备原生回调和 GUI 闭包对旧会话的引用，避免周期刷新累积滞留对象。

刷新会有短暂停顿，不能保证边界处说话无损。它能清除积累的会话状态，但还没有确认长期音质下降的唯一原因，也没有做数小时用户麦克风 / Discord 远端连续验证。若设备被拔掉或推理报错，直接停下并提示，避免无限失败重开；手动停止和退出优先于自动刷新。

验证包含 3,000 / 5,000 包的临界计数、完整尾音、边界手动停止、退出、过期回调和异常处理。真实 GUI / Steam 音频设备使用临时 12 包阈值，确认新旧会话切换、设置保留、旧音频流释放，以及刷新后手动停止不会再次启动。这个加速测试不等于已经跑满 3,000 个真实设备包。

## 启动

计时从 `BackendLauncher` 检查未运行的后端开始，经实际 `start-backend.cmd`（仅测试端口改成 8766），到 `/api/health` 就绪结束。包含依赖检查、模型准备、图和索引加载、三角色真实音频预热和连接探测。每次结束仅停止测试自己创建的进程树，没有复用已运行的后端。依赖、模型和 Windows 文件缓存已经存在，不是重启电脑后的冷启动。

| 配置 | 到就绪 |
| --- | ---: |
| 修改前 0.3.1 基线 | 18.716 s |
| 最终配置，第 1 次 | 7.332 s |
| 最终配置，第 2 次 | 7.119 s |

两次最终测量约 7.1–7.4 秒，比单次旧基线少约 61%。初期候选也出现过 10–11 秒，机器负载会影响结果；不承诺每次达到固定秒数，更没有达到先前估计的 5 秒。1 / 2 / 3 个加载工作线程的探测分别为 7.326 / 7.349 / 7.522 秒，差距很小，最终用最多两个并发任务，未把差异解读为普适结论。

整理成仓库内 `tools/eval/benchmark_startup.py` 后再运行一次为 7.316 秒，摘要也保留在评测目录。

改动如下：

- 已成功验证的模型 SHA-256 持久缓存，键包含绝对路径、文件大小、纳秒修改与创建时间、设备和文件标识及预期哈希。新文件、替换或修改后重新读取；缓存损坏 / 不可写不阻止正常校验。它是本机完整性缓存，不是防御能同时修改缓存和模型的用户。`VOICE_VERIFY_MODELS=1` 强制重算。
- 下载准备阶段避免引入整套推理依赖，常规依赖检查也减少一次 pip 启动。
- 独立图初始化和索引读取可以并发；实际推理预热串行。DirectML 对同一 session 的 `Run` 并发有限制，未并发调用共享图。
- ORT 的共享图优化结果保存在 `.run/ort-cache/`，键含源文件属性、ORT 版本、执行提供者、Windows / CPU 与显卡驱动信息，生成图还有 SHA-256 校验。新模型、驱动等会使缓存失效；不应复制到另一台机器。`VOICE_ORT_CACHE=0` 可关闭。
- 三个 RVC 导出图的优化文件曾实测无法重新加载 DirectML 融合，明确跳过序列化缓存并保留原图。其他缓存读取失败则回退原图；保存失败也可正常推理。
- 本机连接探测使用 100 ms 建连超时，启动轮询间隔降到 100 ms，避免 Windows 对无人监听端口每轮等约 2 秒。建连成功后的 HTTP 响应保留正常超时，慢响应不会立刻触发重复启动。ORT 空闲线程默认不自旋，线程数量仍为 GPU 4 / CPU 1。

首次校验、生成缓存、更新权重或驱动后会更慢。取真实语音处理到第 12 个 120 ms 包时的四个共享图输入（含降噪 / VAD 状态、RMVPE mel 和 ContentVec），分别在缓存图和原图执行，所有输出最大绝对差均为 0。这只是这些输入形状下的对照，不能证明所有可能输入都等价。

复测实际启动脚本（先关闭实时变声，使用空闲测试端口）：

```powershell
.venv-gui\Scripts\python.exe tools\eval\benchmark_startup.py --label local --port 8766
```

## 延迟：保留稳定默认档

上次 0.2.1 的优化是把 VB-CABLE 包长 200 → 120 ms、FIFO 预缓冲 500 → 240 ms、输出设备请求缓冲 150 → 20 ms。此次默认维持这些值，完整的 2,304 样本 / 104.49 ms 前瞻和 DSP 流程也不变。短包试验通过累计输入 / 输出计数，支持音频包短于前瞻时先返回空二进制包，后续补齐，`finish` 保留所有尾音。

48 kHz VB-CABLE 本机回录，预缓冲 240 ms，输出设备实际缓冲约 30 ms：

| 候选 | 灯 / 塔菲 / 爱音，短句延迟 | 结论 |
| --- | --- | --- |
| 120 ms 基线 | 0.731 / 0.710 / 0.742 s | 爱音整段相关性 0.488，不能据此声称本次全部无损 |
| 100 ms | 0.626 / 0.633 / 0.640 s | 三次整段相关性 1.0，短句均零缺包 |
| 100 ms，带噪输入重复 5 次，每角色 47.72 s | 0.561 / 0.601 / 0.880 s | 爱音一次 FIFO 缺包；灯整段相关性 0.828，未通过完整波形检查 |

100 ms 短句约 0.63 秒，但长句不够稳，不能用它代替默认档。GUI 只提供命令行 `--live-packet-ms 100` 的实验选项。80 ms 也已验证协议和样本数，但爱音部分条件推理 95 分位约 124 ms，超过包长，没有作为 GUI 选项。当前延迟不包含 WO Mic 手机网络、麦克风前端和 Discord 网络 / 远端缓冲。

部分回录出现未被 PortAudio 和 FIFO 断流计数反映的采样位置跳变，120 ms 和 100 ms 都遇到。还没证实驱动时钟或系统调度中的具体原因；原始相关性和计数全部保留，没有把“零断流计数”等同于“完整无损”。自动刷新可能限制这类状态积累，但未证实能彻底解决。

72 条合成语音输出的诊断评测：

| 指标 | 既有 120 ms | 实验 100 ms | 实验 80 ms |
| --- | ---: | ---: | ---: |
| 总字错误率 | 8.3% | 8.1% | 7.6% |
| 加噪字错误率 | 18.5% | 19.2% | 17.6% |
| CAM++ 均值：灯 | 0.467 | 0.466 | 0.461 |
| CAM++ 均值：塔菲 | 0.584 | 0.591 | 0.589 |
| CAM++ 均值：爱音 | 0.667 | 0.664 | 0.666 |

100 ms 并非所有条件都更清楚，噪声下还略退步；自动分数不等于人耳音色相似度，也不能把小数点差异当成显著改进。本次默认包长、角色权重与检索比例没有改变。

## 检查范围

- 27 项单元测试通过：自动刷新 11、启动探测 2、校验缓存 6、图缓存 7、样本守恒 1（内部 50 个组合）。无 GPU 或真实设备的边界逻辑和真实音频自检分别记录。
- 真实后端：3 角色 × 4 包长，握手、静音、首包与尾包样本数通过；旧客户端默认 200 ms 不变，160 ms 拒绝。
- GUI / Steam 音频自检：72 通过、0 失败、1 跳过。跳过的是自检中另起后端的用例；上面两次实际启动测量另行覆盖真实脚本启动。没有在通话设备上播放本轮自检音频。
- 实际 VB-CABLE 回录、质量和 ASR 摘要包含失败案例。测试前确认 Discord 当时没有采集 CABLE Output，未改 Discord 设置，也没有把测试语音发进通话。
