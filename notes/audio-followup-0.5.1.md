# 0.5.1 默认 +2、长句接缝与轻尾音

日期：2026-11-15。用户反馈其他角色长时间讲话仍有电流声、塔菲吞尾音、诗歌剧从开始就有电流麦声，并要求四位女性角色默认自动音域再 +2。随后要求完成后把整个项目迁到 D 盘。

## 实际采用的配置

四位角色的 GUI、文件转换、实时重连和周期刷新默认均为 `auto2`，对应自动匹配音域后 `pitch_offset=2`。仍可选模型默认与自动再 +4，没有原声 +4 档。低层 API 省略偏移时仍兼容旧客户端，不强制改变调用方参数。没有更换或重训权重。

| 角色 | 检索比例 / 清音保护 | 最小前瞻 | 接缝淡化 | 输出幅度门控满增益基线 |
| --- | --- | --- | --- | --- |
| 灯 | .75 / .33 | 原值（实时约 104 ms） | 40 ms | .00065 |
| 塔菲 | .75 / .33 | 原值（实时约 104 ms） | 40 ms | .00045 |
| 爱音 | .75 / .33 | 原值（实时约 104 ms） | 40 ms | .00065 |
| 诗歌剧 | .4 / .1 | 至少 160 ms | 40 ms | .00065 |

门控门槛仍会随残余背景抬高；塔菲的调整只减少已被 VAD 接受的轻声衰减，静音 / 无语音活动仍为零。没有把原始有声波形混进 100% 强度的结果。诗歌剧增加前瞻约 56 ms，换取包边缘更多上下文；握手回传实际前瞻，客户端正确处理启动时的空输出。

原有接缝为 320 / 22050 秒，约 14.5 ms；现在四位本机配置均为 40 ms。作为参考，[固定版本 RVC GUI](https://github.com/RVC-Project/Retrieval-based-Voice-Conversion-WebUI/blob/d60cd3d009b7e438f92f8624fa89b710d10c6a39/gui_v1.py)的默认交叉淡化是 50 ms。仍沿用本项目的 SOLA 对齐和分频能量补偿，不能把延长淡化本身当作消除所有电流声的证据。包长、VB-CABLE 320 ms 目标缓冲和自动刷新流程没有改变。

## 对照与未采用的尝试

诗歌剧初轮两句合成男声共 36 字：旧 +4 错 3 字，仅改 +2 错 1 字，+2 配 .4 / .1 错 0 字，另降目标至 330 Hz 错 1 字。六段、113 字的扩展对照中，+2 原参数与 .4 / .1 均错 5 字。小样本不能证明普遍改善；用户听初轮 B 后认为更清楚，但仍有爆音，并指出样本太短、两侧都没有电流音。因此采用 B 的检索 / 保护设置，保留 417.4 Hz 初始自动目标，没有声称短样本验证了去电流音。

塔菲曾试 .15 清音保护、较软门控与较长淡化的组合，六段 113 字从 2 错变成 4 错。最终恢复 .33 清音保护，只保留门控和淡化调整；该被拒绝组合的识别结果不能用作最终版本的提升数字。

经用户同意，另做过一次 WO Mic 采样，原始与四条转换音频仅存在内存，没有保存或上传。输入与四条输出的轻声结束语均被识别完整，未复现用户描述的严重吞尾音。ASR 完整不能证明尾音听感和杂音正常，这不是系统性的真人远端评测。

## 推理实现与持续状态检查

`tools/eval/check_rvc_backends.py` 对诗歌剧的一个有声窗口，在相同特征、F0、潜变量和固定激励噪声下，对照上游原生 PyTorch 生成器、CPU ONNX 和 DirectML：

| 对照 | 最大绝对误差 | RMSE | 信噪比 |
| --- | --- | --- | --- |
| PyTorch / CPU ONNX | 8.02e-6 | 7.85e-7 | 98.66 dB |
| CPU ONNX / DirectML | 1.77e-5 | 1.30e-6 | 94.30 dB |

仅说明这个匹配窗口没有明显生成器导出 / 执行差异，没有比较完整原版实时应用，也未安装完整 VCClient。诊断图和输入留在 `.run/`，没有替换生产推理图。

`tools/eval/check_stream_drift.py` 用合成短句、停顿和固定底噪重复 90 秒，检查塔菲与诗歌剧的持续状态：两者各 49,503 个有声基频帧，语音活动之外的有声帧为零；15～75 秒的残余底噪估计约 3.8e-5～4.3e-5，没有持续上升。音域估计随语句位置变化，没有据此认定长期漂移是根因。因此没有加入未经证实的基频强行归零或底噪上限补丁。

上述输入都不足以完整复现用户长时间讲话的电流声。声音与目标差异大可能使高音移调 / 模型发音更难，但不能仅靠这点解释随时间恶化。

爱音的大索引还暴露了处理余量问题：相同 50 条索引向量作查询、重复 40 次，2 / 4 线程的检索中位耗时为 15.87 / 8.77 ms，95 分位为 22.83 / 9.91 ms，邻居编号相同、距离在容差内一致。现仅对至少 100,000 向量的索引使用最多 4 线程，其他仍为 2 线程；不改变检索比例、近邻数或 nprobe。

目录中已有的启动提速改动只预热首个角色。增加线程后，爱音首次有声包仍测到约 280 ms 峰值并缺包。现后台加载每个角色时先用固定输入预热其独立生成器，再标记可用；这不是对共享 ContentVec / RMVPE 并发做完整转换。保留加载进度页、首角色先就绪与其他角色后台加载的流程，并修复已运行后端返回 503 时又启动重复进程的问题。

## 本机回录、回归与迁移

48 kHz 文件模拟麦克风，120 ms 包、100% 强度、自动再 +2，经 CABLE Input 写入并从 CABLE Output 实际录回。每条输入约 102 秒，含重复句子、人工底噪与停顿，不是连续真人讲话。

| 测试 | 播放缺包 | 整段 / 最差有声秒相关性 | 本机延迟 |
| --- | --- | --- | --- |
| 灯首轮 | 0 | 1.00000 / 1.00000 | .678 s |
| 塔菲首轮 | 0 | 1.00000 / 1.00000 | .671 s |
| 诗歌剧首轮 | 0 | 1.00000 / 1.00000 | .762 s |
| 爱音首轮（复制文件期间） | 1 | 1.00000 / 1.00000 | 2.040 s |
| 爱音复制结束后单独复测 | 1 | .66646 / -.02627 | 1.048 s |
| 爱音 4 线程、未补生成器预热 | 1 | .56711 / -.29342 | .912 s |
| 爱音 4 线程并补预热后 | 0 | 1.00000 / 1.00000 | .670 s |

失败轮完整保留。整段相关性允许对齐一个总延迟，因此可能在缺包发生于开头时仍为 1；必须同时看缺包、分段和延迟。最终爱音每包耗时的 95 分位 74.5 ms、最大 181.5 ms。其余三位的约 102 秒结果来自前一轮相同音频配置，没有把后来界面短测试冒充第二轮长测试。均未发生输入录回溢出、FIFO 丢样本或满幅削波。回录只验证发送与虚拟线播放是否一致，不能证明模型本身没有滋滋声；延迟不含 WO Mic / 手机和 Discord。

真实 GUI / 后端 / 设备自检 **85 通过、0 失败、1 跳过**，覆盖四角色默认 +2、切角色的关闭 / 淡出 / 重开，以及自动刷新后的真实 CABLE Output 回录；跳过另起第二后端，迁移后另测真实启动。**45 项单元检查**通过；**12 组声线 / 音高组合与 16 次非法请求**通过。
